# Zed 上での表示に関する所見

`docs/tech-stack-evaluation.md` 8. の「未検証・要確認事項」のうち、Code Lens
表示（P5）に関わるものを引き取るための文書。

## この文書の読み方

2 節のチェックリストは **一部だけ確認済み** である。所見が書いてある項目が確認済みで、
所見が空のままの項目は未確認。埋めるのは実機を持っている人間であり、推測を所見として
書かないこと。書くときは、確認した Zed のバージョンと OS も併記する。

3 節の実測値は Zed 無しで測れたもので、**実測である**。測り方は 4 節に書いた。

## 1. 前提（一次情報で確認済み・再調査不要）

Zed のソース（`main`、2026-08-27 時点 `f66ed399`）で確認済みの挙動。これらは
実機確認の対象ではなく、実装がすでに従っている前提である。

2026-08-30 に、実際に動かしている 1.17.2（`c8e44cf`）でも同じであることを確認した。
`height: Some(1)` と `BlockStyle::Spacer` は変わっていない。

- Code Lens は対象行の**上**に独立したブロックとして挿入される
  （`crates/editor/src/code_lens.rs` の `BlockPlacement::Above`）。
- 表示テキストは `CodeLens.command.title` だけ。`command` を持たないレンズ、
  および title が空のレンズは描画されない。→ `codegloss.noop` を付けている。
- ブロックの高さは 1 行固定。訳文に改行を入れても 2 行にはならない。
  → サーバ側で改行を空白に潰し、120 文字を超える訳文は `…` で切っている。
- 同じ行に複数のレンズがあると `" | "` で連結されて 1 ブロックになる。
  → 訳文中の `|` は全角 `｜` に置換している。
- 既定は `"code_lens": "off"`。**インストールしただけでは何も表示されない。**
- **`code_lens` はグローバル専用の設定で、`.zed/settings.json`（プロジェクト設定）
  からは効かない。** 1.17.2 でこの設定を読んでいるのは 3 箇所（`editor.rs:2622`、
  `editor.rs:9995`、`code_actions.rs:543`）で、すべて `EditorSettings::get_global`。
  `SettingsStore::value_for_path(None)` はグローバル値を返すだけで、ローカル設定が
  グローバル値に合流するのは `disable_ai` だけである（`settings_store.rs` の
  `recompute_values`）。同じ `.zed/settings.json` に書いた `lsp.*` が効くのは、
  あちらが `LspSettings::for_worktree()` という位置を見る API で読まれるため。
  この非対称は踏みやすい。**設定は `~/.config/zed/settings.json` に書くこと。**
- タイトルを入れる `div` には幅制限も `overflow` も `text_overflow` も無い。加えて
  Zed の既定は `soft_wrap: "none"` / `preferred_line_length: 80` で、既定の `Rust` に
  これらの上書きは無い（あるのは `format_on_save` と `debuggers` だけ）。つまり
  レンズは折り返しもされず、エディタのペイン幅を超えた分は画面外に出る。ただし
  ブロックは `BlockStyle::Spacer` なのでバッファと一緒に水平スクロールする
  （`element.rs` の `layout_blocks` が `Sticky` 以外には `-scroll_pixel_position.x`
  を足す）。右にスクロールすれば読めるので、失われるわけではない。→ 2.5

## 2. 実機確認チェックリスト（一部確認済み）

Zed の設定に `"code_lens": "on"` を書き、`codegloss-lsp` が起動している状態で
Rust ファイルを開いて確認する。

確認した環境:

- Zed のバージョン: 1.17.2+stable.349（`c8e44cf`）
- OS: WSL2 / Ubuntu 24.04.1 LTS（Linux 5.15.167.4-microsoft-standard-WSL2）
- 確認日: 2026-08-30 〜 2026-08-31
- エディタのペイン幅: 約 100 桁

確認には使い捨ての Rust ファイルを使った（リポジトリには残していない）。要点は、
10 桁ごとに位置を示す次の目盛りコメントを 1 ブロックとして置くことである。これが
あると、レンズが画面のどの桁で切れているかを目視で特定できる。

```rust
// ....5...10....5...20....5...30....5...40....5...50....5...60....5...70....5...80....5...90....5..100....5..110....5..120....5..130
```

翻訳エンジンが Passthrough でコメントの原文がそのままレンズに出るため、日本語の
描画を見たいときは日本語のコメントを書けばよい。

なお WSL や素の Linux コンテナでは、日本語フォントが入っていないと訳文が □ になり
2.2 の判定ができない。Ubuntu なら `fonts-noto-cjk` を先に入れておくこと。

### 2.4 クリックとコマンド

- [ ] レンズをクリックしてもエラーダイアログが出ない（サーバは `null` を返す）
  - 所見:
- [x] `"code_lens": "menu"` にしたときの見え方。コードアクションメニューの中に
      訳文が並ぶはずだが、実用になるか
  - 所見: **実用にならない。** 理由は 2 つある。

    1. `menu` にすると行の上のブロックは消える（`EditorSettings.code_lens.inline()`
       は `On` のときだけ true）。訳文はコードを読んでいる最中には見えず、メニューを
       開いたときだけ現れる。読解支援としては本末転倒である。
    2. **コメント先頭行の 0 桁目にカーソルがあるときしか出ない。** 1 桁でもずれると
       消える。実機で確認した（行頭に置くとメニューの先頭に訳文が出る。同じ行の
       途中に置くと出ない）。

    2 の原因は `Project::code_lens_actions` の絞り込みが「選択範囲がレンズの range
    に含まれるか」であること。

    ```rust
    tagged.retain(|_, action| {
        range.start.cmp(&action.range.start, &snapshot).is_ge()
            && range.end.cmp(&action.range.end, &snapshot).is_le()
    });
    ```

    CodeGloss のレンズは range が空（`code_lens.rs` の `lens()` が
    `(line, 0)..(line, 0)` を返す）なので、カーソルがちょうどその 1 点にあるときしか
    通らない。range にコメントブロック全体の幅を持たせれば 2 は解消できるはずで、
    `on` 側の描画位置は `range.start` の行だけで決まるため影響しない。ただし 1 が
    残るので、`menu` を主たる表示方法にする道は無い。この設定は「行に対する操作」を
    畳むためのものであって、行の内容を見せる用途は想定されていない。

### 2.5 共存

- [ ] rust-analyzer のレンズ（`Run`、`Implementations` など）と同じ行に来たとき、
      `" | "` で連結されて 1 行になる。訳文が混ざって読めなくならないか
  - 所見:
- [x] 長い訳文が `…` で切られたとき、続きをホバーで読む導線が自然か
  - 所見（サーバ側・実測）: サーバは仕様どおり切っている。上の目盛りと、長さの
    違う日本語コメントに対する `textDocument/codeLens` の返り値は次のとおり。

    | 対象 | 文字数 | 表示カラム | `…` が付くか |
    |---|---|---|---|
    | 日本語の長いコメント | 120 | 230 | ○ |
    | 半角の目盛りコメント | 120 | 120 | ○ |
    | 日本語の中くらいのコメント | 74 | 135 | × 120 文字未満なので切らない |

    `MAX_TITLE_CHARS` は**文字数**で数えているが、レンズに効く制約は**表示カラム幅**
    である（日本語は East Asian Width が W/F で 1 文字 2 カラム）。3 行目のように
    打ち切りに達しない訳文でも、カラム幅では 100 桁を超える。
  - 所見（画面側・実測）: **このペイン幅ではクリップは起きず、3 件とも 1 行に収まって
    見えた。** 半角 120 カラムのレンズは `....5..110....5..12…` と末尾の `…` まで、
    日本語 230 カラムのレンズも `どうかをここ…` まで、打ち切っていない 135 カラムの
    レンズも句点まで見えている。したがってペインは**レンズ換算で 230 カラム以上**ある
    （レンズは 0.9 倍フォントなのでバッファ換算では約 207 桁以上）。
    `…` は意図どおり画面に出ており、続きをホバーで読む導線も成立している。

    狭いペインでどう見えるかは未確認。ただしブロックは水平スクロールするので
    （1 節）、画面外に出ても右にスクロールすれば読めるし、全文はホバーで読める。

    残る論点は `MAX_TITLE_CHARS = 120` という値の妥当性だけである。`code_lens.rs`
    のコメントは「1 行に収まらないと画面からはみ出るから切る」としているが、日本語
    120 文字は 240 カラムでどのみちはみ出るので、この値は書かれた目的を果たして
    いない。バグではなく仕様の見直しなので、必要になったら別途起票する。
    （この件は一度 Issue #10 として起票したが、症状の誤読だったので閉じた。）

    なお一度は「レンズがペイン幅 100 桁でクリップされる」と記録したが、それは誤りで、
    そのとき `code_lens` は 1 節の理由で無効のままだった。見ていたのはホバーの
    ポップアップである。
  - 所見（ホバー側）: ホバーは `single_line()` を通さず全文を返し（`backend.rs`）、
    ポップアップ側も `hover_popover.rs` の `.max_w(max_size.width)` で折り返すため、
    切られずに読める。ここは成立している。

## 3. 性能の実測値（Zed 無しで測定・実測）

`tech-stack-evaluation.md` 8.3「大きなファイルでコメント数が多い場合の再計算
コスト」に対応する。**Zed は使っていない**ので、ここにあるのはサーバ側の
コストだけである。エディタ側の描画コストは 2 節と同じく未確認。

### 測定環境

- CPU: Intel Xeon @ 2.10GHz / 4 コア（コンテナ内）
- ビルド: `cargo build --release -p codegloss-lsp`（rustc 1.98.0）
- 翻訳エンジン: `PassthroughTranslator`（入力をそのまま返す）。
  **実モデルの推論時間は含まない。** ここで見えているのはコメント抽出・
  キャッシュ参照・レンズ生成・JSON の往復だけである。

### 1000 行 / コメントブロック 333 件

`scripts/measure-code-lens.py` の既定値。30 回試行の min / median / max。

| 測ったもの | min | median | max |
|---|---|---|---|
| warm `textDocument/codeLens`（全件キャッシュヒット） | 1.4 ms | **1.7 ms** | 3.1 ms |
| `didChange` 送信 → `codeLens` 応答（再抽出を含む） | 8.2 ms | **8.9 ms** | 12.8 ms |
| `didChange` → `codeLens/refresh` 到着 | 235 ms | 292 ms | 293 ms |

- cold（`didOpen` 直後、訳が 1 件も無く 333 件すべてがプレースホルダ）の
  `codeLens` は **約 10 ms**。
- `didOpen` から最初の `codeLens/refresh` が届くまでは **約 161 ms**。うち
  150 ms は `translation.rs` の `DEBOUNCE`。
- 3 行目の 292 ms は仕事の重さではない。`translation.rs` の
  `MIN_REFRESH_INTERVAL` が refresh を 300 ms に 1 回までに絞っており、この
  ループは 300 ms より速く次の編集を投げているので、値は「直前の refresh から
  300 ms」から `codeLens` の往復分を引いたものに張り付く。連続編集でも
  エディタに再取得を頼むのは 300 ms に 1 回まで、という設計どおりの数字である。
- 2 行目から 1 行目を引いた **約 7 ms** が、Tree-sitter の再パース・コメント
  再抽出・翻訳ジョブの投入にかかっている分（差分からの見積もり）。

### 行数を変えたときの傾向（各 20 回試行の median）

| 行数 | コメントブロック | cold codeLens | warm codeLens | `didChange` → 応答 |
|---|---|---|---|---|
| 998 | 333 | 10 ms | 1.7 ms | 8.9 ms |
| 2996 | 999 | 23 ms | 4.8 ms | 21 ms |
| 5000 | 1667 | 36 ms | 8.3 ms | 35 ms |

ほぼ線形。1000 行規模なら 1 桁 ms で、キーストロークごとに再計算しても
問題にならない。5000 行・コメント 1667 件でも 35 ms 程度で、
`textDocument/codeLens` は編集のたびに飛ぶ種類のリクエストではない
（`didChange` のあと Zed が取り直すタイミングに依存する）ため実用上は余裕がある。

上の数字はすべてコメント抽出・キャッシュ参照・レンズ生成の側なので、実モデル
（P7）に替えても変わらない。**変わるのは「訳が出るまでの時間」だけ**で、それは
モデルの推論時間そのものである（`tech-stack-evaluation.md` 8. の 4 番、FuguMT の
実機レイテンシ）。翻訳がリクエストの外で走る設計のおかげで、推論が何秒かかっても
`codeLens` の応答時間には出ない。

## 4. 測り方（再現手順）

```console
$ cargo build --release -p codegloss-lsp
$ python3 scripts/measure-code-lens.py            # 1000 行
$ python3 scripts/measure-code-lens.py --lines 3000 --rounds 20
```

python3 が要る（標準ライブラリのみ。追加パッケージは不要）。Nix の dev shell には
python3 を入れていないので、そこで動かすなら `nix shell nixpkgs#python3` を挟む。

スクリプトはリリースビルドのサーバを子プロセスとして起動し、stdio 越しに
`initialize` → `didOpen` → `codeLens` → `didChange` → `codeLens` を投げて
往復時間を測る。サーバから飛んでくる `workspace/*/refresh` にはその場で応答を
返す（返さないと翻訳ワーカが次に進まない）。

`didChange` の直後に投げた `codeLens` が、本当に**変更後の**バッファに対する
答えかどうかは、スクリプト自身が検証している。毎回 1 件だけコメントを書き換え、
その 1 件だけが `⟳ 翻訳中…`（＝キャッシュミス）で返ってくることを assert して
いる。順序が逆なら 0 件になるので測定値が無意味になったと分かる。
